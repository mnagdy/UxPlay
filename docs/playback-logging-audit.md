# Playback logging audit — 10 September 2026

The logging in the initial software preview could not identify the cause of the reported HEVC failure. It established that the playback timeline stopped; it does not distinguish missing media, malformed packets, decode failure, synchronization wait or blocked output. The diagnostic changes described below address verified gaps. They are not a fix for the failing stream.

## Evidence and limits

The user confirmed picture and sound for direct HTTP H.264 at 1280×720/25 fps. The failing photo identifies **HEVC at 1280×720/25 fps**, software decoding, position zero, unknown audio format/output and a grey malformed first picture. This is not exclusively a 4K throughput problem. During one two-second sample the player used about 1% CPU and its threads were sleeping; that sample does not support CPU saturation. TCP CLOSE_WAIT is not proof of truncated media or starvation.

Generated HEVC Main and Main10 at 720p25 with AAC passed native software playback through null outputs, both as MP4 and as MPEG-TS/fMP4 HLS. That establishes basic installed decoder/demuxer capability for those files, not compatibility with the failing source or physical HDMI/audio output.

## What the revised capture records

In screen debug mode the receiver writes one typed playback summary every two seconds while a child is active and on state/lifecycle changes. Stable idle snapshots are not repeatedly written. Each snapshot contains its own session and monotonic timestamp, player PID, knownness flags, per-stream cache/timeline observations, selected tracks, decoded-format evidence, requested/observed state, observed decoder/output path, separate drops, warning/error classifications, terminal reason and capture-health counters. Request/control/output-release records make the transition around these snapshots reconstructable. No per-frame printing is introduced.

`scripts/pi-playback-report --host mo@192.168.1.124 --output report.json` collects a bounded recent window without restarting the service or opening its private IPC. The report includes runtime/build identity where available and only recognized typed diagnostic records from the journal. It reports omitted, rejected and truncated records. Boot ID + receiver PID + session identify an attempt; session number alone can repeat after a process restart. Debug mode additionally retains a private current file and one rotated file, each limited to 1 MiB, under the receiver user's state directory. The exporter reads that bounded history as well as the current journal, so a reboot does not automatically discard the previous attempt. This is a recent history whose time coverage depends on playback activity, not an unlimited archive. Current runtime metadata describes the current process; it must not be silently assigned to records from another boot or PID.

Warnings are observations, not automatically fatal causes. A later healthy frame can recover from a warning. Cache occupancy is not network byte count, and a cache reader PTS is not a decoded-frame or audible-sample count. An observation age is the time since an available property update, not independently measured time since source traffic or hardware presentation.

## Evidence still unavailable in stock mpv

Stable mpv IPC does not provide trustworthy per-selected-track compressed-packet counts, decoded-frame/sample counts or successful HTTP request identities/completion timings. `estimated-frame-number` is derived from playback position and must not fill that gap. A nonzero cache can belong to only one track. Per-stream fields can themselves be unavailable.

On the installed mpv 0.40/FFmpeg build, successful HTTP status/range headers require trace logging. A generated one-second fixture produced roughly 1,400 trace events. These lines omit a reliable request identity, so concurrent HLS requests cannot be correlated by adjacency. Always-on global trace, a competing player, or a new proxy would add overhead or change the path under investigation. They are not part of this revision.

If the revised capture shows a stall without a discriminating cause, the next work is a **targeted instrumentation hook or controlled same-media experiment chosen from that capture**. For example, occupied video cache with absent audio format needs audio/demux/synchronization evidence; HTTP/HLS failure needs transport evidence; missing-reference reports need packet completeness and decode evidence. Do not silently infer an answer from a zero counter or switch hardware/buffering policy again.

## First live diagnostic result and targeted packet capture

The user activated release `20260910T180950703731Z-52c2997e3800-dirty`; the 18:24 UTC report verifies its running binary. In session 3, HEVC Main 1280×720/25 software playback stays at position zero, with the video cache reader at 0.2 seconds while its cache grows from 18.92 to 108.92 seconds. Pause is false; core idle and cache underrun are true. AAC is selected, but audio cache timestamps, decoded format and output remain unavailable. No classified HTTP/HLS failure or diagnostic capture loss appears in this attempt.

Session 2 is a useful H.264 comparator: AAC 48 kHz stereo initializes, ALSA is selected, and both timelines advance. It also records one video-output error, and its much larger startup decode-error count stops growing during successful playback. Neither the shared output error nor one early missing-reference error establishes why HEVC remains stalled. Session 2's playlist-reload failure occurs after the accepted pause, before replacement.

The next observation is therefore compressed audio reaching the selected decoder queue. Debug mode now requests a **30-second startup capture** using mpv's narrowly selected `lavf` trace module and `terminal-default` log subscription. Only the exact, version-tested `append packet to audio/video` grammar becomes counters, byte counts and finite timestamp observations. These counts describe selected queues by media type, not individual track IDs, decoded frames, network requests or rendered output. A valid PTS of zero is distinct from mpv's missing-timestamp sentinel. No per-packet records are written to disk. After the window, the owner disables packet verbosity and places a fixed marker in the same player log queue. It counts queued packets through that marker before ending capture, then restores warning-level logging. A missing marker, packets arriving after the marker, rejected grammar, overflow or command failure makes capture incomplete and cannot change playback policy.

The first generated positive test exposed a logger naming trap: `demux=trace` did not activate the actual `lavf` logger. An acknowledged subscription with zero counters is insufficient evidence. Capture acceptance requires that the supported packet grammar is actually observed, plus successful verbosity restoration and no capture-loss indication. The audio-starvation interpretation requires positive video packet evidence with zero audio packets, rather than treating two unverified zero counters as proof.

Warning capture also retains the last fixed stage and reason even when classification is unknown. Added classes cover MPEG-TS packet corruption/PES size mismatch, packet-read errors, HLS sequence changes and expired segments, plus unavailable virtual-terminal control separately from frame-presentation/DRM errors. Raw messages and source locations still do not enter a report.

The later YouTube session 7 is a separate failure pattern: cached HLS H.264 High 1920×1080 at about 23.98 fps advances with initialized AAC/ALSA and ample cached data, while video-output drops increase by about 7–8 per second. The selected decoder is software; this does not alone prove whether decode or presentation is limiting. Qualify H.264 acceleration and physical presentation separately from the HEVC audio-startup investigation.

## Validation and next real-device capture

The diagnostic tests must verify bounded file rotation, file permissions and symlink refusal, warning-only HTTP/decode causes, late terminal logs, rejected/unknown properties, actual pause differing from requested state, decoded versus container metadata, per-track cache knownness, first-position baseline, stale generations and malicious metadata/log text. Report tests must reject URLs or unknown text even when prepended with a recognized diagnostic prefix and must enforce record/byte/time limits. Native tests use null outputs and do not certify HDMI playback.

After the completed diagnostic release is selected, capture one known-good H.264 session, the **same failing HEVC item**, stop, then H.264 recovery. Keep software decoding and current output settings constant. Record picture and sound separately. The success criterion for this investigation is an identified failure stage with supporting evidence, followed by a targeted fix that passes the actual failing source and recovery sequence. “The build passed” and “more fields appeared” are not that criterion.

## Source checks

The audit checked current local coordinator, renderer, protocol and adapter code and the installed Pi player with generated-only HTTP fixtures. Version-specific behavior was checked against [mpv 0.40 properties](https://github.com/mpv-player/mpv/blob/v0.40.0/DOCS/man/input.rst), [mpv client event ordering](https://github.com/mpv-player/mpv/blob/v0.40.0/player/client.c), [video decode logging](https://github.com/mpv-player/mpv/blob/v0.40.0/video/decode/vd_lavc.c), [audio startup synchronization](https://github.com/mpv-player/mpv/blob/v0.40.0/player/audio.c), and FFmpeg's [HTTP](https://github.com/FFmpeg/FFmpeg/blob/n7.1.2/libavformat/http.c) and [HLS](https://github.com/FFmpeg/FFmpeg/blob/n7.1.2/libavformat/hls.c) implementations. Exact log grammar remains version-dependent; unmatched text is counted and discarded.
