# AirPlay receiver robustness research — 13 September 2026

This is a source review, not a claim of restored iPhone playback. GitHub repositories were fetched live; issue bodies were opened, rather than relying on search snippets. Local implementation was inspected in `/Users/mo/Documents/ChatGPT/TV/UxPlay`. The companion [implementation audit](2026-09-13-airplay-reliability-audit.md) records the changes and validation.

## Main conclusions

The important boundary is between AirPlay negotiation/session ownership, fetching the source, and decoding/output. Swapping mpv or GStreamer affects the last part. It cannot fix a playlist exchange that fails before the player starts, incorrect association of the phone's several connections, stale ownership, or a worker that exits without becoming restartable. The local E3 evidence is in the playlist preparation stage, so it is not evidence against either decoder.

The public receiver projects do not provide an obvious complete replacement with demonstrated lower failure rates. UxPlay remains the closest fit for this project's combination of mirroring and direct video. Shairport Sync is the strongest separate audio-only experiment. RPiPlay shares UxPlay's ancestry and several recovery weaknesses, and lacks its direct-video component. Rewriting the application language would not itself add the missing protocol behavior, fix sender-generated streams, or repair a kernel driver stuck during shutdown.

## Protocol boundaries to preserve

AirPlay is a family of protocols. The public reverse-engineered specification explicitly says it is incomplete and describes older Apple TV/iOS versions; its state semantics are useful, but a modern wire change must be validated against an actual sender. [Specification introduction](https://openairplay.github.io/airplay-spec/).

For direct video, `/play` supplies the source location and initial position. `/rate`, `/scrub`, `/stop` and `/playback-info` provide controls and actual readiness/buffering feedback. The reverse connection carries receiver-to-phone events; the published event vocabulary includes loading, playing, paused and stopped. [Video controls](https://openairplay.github.io/airplay-spec/video/http_requests.html), [video events](https://openairplay.github.io/airplay-spec/video/events.html), [reverse upgrade](https://openairplay.github.io/airplay-spec/photos/http_requests.html#post-reverse).

UxPlay's YouTube path adds an application-specific relay: the receiver sends `unhandledURLRequest` over the reverse connection, and the phone answers with `unhandledURLResponse` and FCUP response fields. The receiver obtains the master and child playlists and exposes rewritten local manifests to the player. Ordinary HTTP/HTTPS streams can bypass this relay. Consequently a session needs several related identities: Apple session, playback UUID/cache generation, individual FCUP request ID and reverse socket. These cannot safely be replaced by one global “current connection”. The code is the primary reference for this extension; the old public spec does not completely describe it. [Upstream FCUP implementation](https://github.com/FDH2/UxPlay/blob/44024fe07f7f61d459de383e8a1047acdb0c7555/lib/fcup_request.h), [upstream HTTP handlers](https://github.com/FDH2/UxPlay/blob/44024fe07f7f61d459de383e8a1047acdb0c7555/lib/http_handlers.h).

Local `renderers/screen_status.h` assigns numeric value 3 to `SCREEN_ERROR_SOURCE`; `screen_status.c` prints it as E3 and labels it “Stream data unavailable”. This is this project's display code, not an Apple-defined E3 diagnosis. The retained `docs/playback-findings.md` records failures before mpv started, including receipt of a master and language selection on 13 September. The exact failing field was not recorded in that evidence. Do not identify a particular YouTube codec, language, or network defect from E3 alone.

FairPlay Streaming is a separate compatibility boundary. Apple's description explicitly includes secure key exchange and protected playback, not merely AES decoding of media bytes. A player switch cannot supply an absent licensed key-delivery path. This matches the local Channel 4 evidence, but that evidence is separate from YouTube E3. [Apple FairPlay Streaming](https://developer.apple.com/streaming/fps/).

## Architectural improvements worth a separate decision

1. Give each accepted playback attempt one owner and generation, with explicit preparing/playing/paused/failed/stopping/idle states and bounded transitions. Close/release only that attempt's associated control, reverse, cache and transport resources. “Process alive”, “phone responding” and “media advancing” are separate observations.
2. Make source failure a terminal protocol state, not only a local display change. Inspection found only FCUP `/event` generation locally, not receiver-originated playback-state events. A correctly session-scoped `stopped` event and accurate `/playback-info` may help the phone leave a failed route. This is an inference from the published state protocol; modern sender captures and ACK behavior must validate it before deployment. Avoid inventing an Apple E3 response.
3. Keep media decoding/output in a supervised process where practical, so it can be replaced without retaining protocol ownership. Existing mpv process isolation is useful. A kernel task stuck in uninterruptible driver code remains outside what killing a player can guarantee.
4. Before replacing GStreamer audio, compare Shairport Sync with the same sender/network/output and exercise starts, pause/resume, app replacement and packet interruptions. Tune retransmission only with observed deadlines/duplicate rates, not a larger buffer by default.
5. Add a synthetic fault suite: late/duplicate FCUP replies, reverse socket loss, missing child manifests, split request bytes, truncated mirror packets, media worker exit, no-first-frame timeout, backend exit and repeated reconnect. The acceptance criterion is that the next attempt works without changing the phone's network or closing its apps. A real iPhone must still verify that criterion.

## Mirror defects repaired by this audit

The source audit found additional concrete defects beyond the already-backported upstream fixes: short encrypted packets could consume more residual keystream bytes than their own length; stopped mirror and audio receive workers stayed unjoined and prevented restart; header EOF leaked its old descriptor; partial packet/codec buffers leaked on exit; malformed NAL/configuration lengths were used before validation; periodic video report plists were never released. Those files were patched and focused regressions added. Native UBSan passed the buffer and packet tests. macOS AddressSanitizer itself failed at runtime startup; the root audit runs the full transport regressions in the shared Linux build/runtime. This is code-level validation, not projector acceptance.

The audio-worker case is reachable when `select` fails: it exits and clears `running`, while the old stop routine skipped cleanup because `running` was already false. Its fix matches the mirror fix. NTP has the superficially similar guard but its current worker does not independently exit on send/receive errors; no NTP change was made on this evidence.
