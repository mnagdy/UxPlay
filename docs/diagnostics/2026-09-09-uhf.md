## HEVC hardware verification at 12:54–12:56 BST

The additional decoder concern is now resolved for the sampled 720p HEVC stream. The original generic `fakesink` comparison was not a representative hardware-output test. GStreamer 1.26.2's stateless HEVC decoder advertises only system-memory formats when downstream accepts unrestricted `ANY` caps, and DMA-DRM allocation requires video metadata support. The Pi's purpose-built `fakevideosink` supports that negotiation: the original hardware decoder produced the first frame in 247 ms, with 121 sink-rendered frames and no drops over five seconds. Its output was DMA-DRM NV12 with modifier `0x0700000000000004`.

A parallel-process `kmssink` probe negotiated and decoded successfully, but both hardware and software modes then hit `drmModeSetPlane` errno 13 (`EACCES`). Inspection showed the running receiver owned `/dev/dri/card1`; this was contention with the receiver's display ownership, not a decoder-format failure. `playbin3` in GStreamer 1.26.2 also does not implement the `FORCE_SW_DECODERS` flag. The corrected probe's software comparison disabled only the HEVC hardware decoder within that test process; it changed neither the receiver process nor the on-disk plugin registry.

The decisive comparison therefore used the running receiver's own AirPlay HTTP `/play` control with the same local, video-only live-HLS fixture. Session 7 began at 12:55:49 BST. It selected `v4l2slh265dec`, delivered a decoded frame to the actual `kmssink` at 3.856 seconds, and entered PLAYING at 3.925 seconds. The 15-second observation produced no diagnostic errors or warnings; `/stop` returned 200 and the receiver logged the stop at 15 seconds. Its service and configuration were not changed. This confirms the sampled HEVC decode/display pipeline; physical projected image quality was not independently observed, and this fixture intentionally had no audio.

The opt-in source `UxPlay/tests/hls_probe.c` builds independently against GStreamer and supports bounded auto/software comparisons with `kmssink`, `fakevideosink`, or `fakesink`. It emits selected decoder, format, first-buffer timing, rendered/dropped counters and allowlisted error operation/errno; it suppresses raw URLs, headers and GStreamer error text. Captured media and detailed private logs remain outside Git under the Pi's private diagnostic fixture directory. At that point the short test gave no justification for a fallback. The later real UHF stop described below supersedes that conclusion: it proves a kernel shutdown hang that the short fixture did not reproduce.

Primary implementation reference: [GStreamer 1.26.2 stateless HEVC negotiation and allocation](https://github.com/GStreamer/gstreamer/blob/1.26.2/subprojects/gst-plugins-bad/sys/v4l2codecs/gstv4l2codech265dec.c#L374).

## Confirmed display startup delay

An isolated `kmssink` NULL-to-READY comparison on the Pi identified a second, independent cause of slow channel startup. With default driver discovery, initialization took 3,619 ms and 4,047 ms in two runs. Setting the sink's existing `driver-name` property to `vc4` reduced both corresponding runs to 155 ms. All four state changes succeeded; the probe supplied no media and performed no frame rendering. The running receiver remained unchanged.

The upstream sink's default discovery tries thirteen other DRM driver names before `vc4`. The production video-only playback trace spends roughly this interval before sink attachment, so specifying the known Pi display driver should save several seconds each time a playback pipeline creates a new sink. This should be scoped to the Pi profile and must preserve explicit user driver/device choices. It does not resolve sender-side media delays or empty-audio buffering. Source: [GStreamer 1.26.2 `kms_open` driver discovery](https://github.com/GStreamer/gstreamer/blob/1.26.2/subprojects/gst-plugins-bad/sys/kms/gstkmssink.c#L475).

No service playback settings or receiver logic were changed during this investigation. Receiver fallback could avoid an indefinite wait, but cannot reconstruct audio samples absent from the sender's stream. UHF's audio selection/conversion on affected channels remains to investigate; general startup latency and other channel formats remain separate work.

## Recovery build activated; HEVC teardown hang confirmed, 13:21–13:33 BST

The user activated release `20260909T121852093658Z-52c2997e3800-dirty` at 13:21:07 BST. PID 9567 logged the vc4 selection at startup. YouTube session 1 reached its first actual kmssink buffer in 791 ms and PLAYING in 1.720 seconds. The user confirmed that YouTube works very well.

UHF session 2 began at 13:22:21. Its initial HTTP manifest had two entries, target duration 10 seconds and no ENDLIST. About 4.7 MB of parsed media was already available, covering 19.16 seconds of video with zero queued audio. The first missing-audio repair did not occur until 10.197 seconds, after the next segment arrived. The helper conservatively skipped the first coalesced initialization/segment boundary, causing this extra wait. The new helper accepts that first boundary only when no prior media box has been seen, retaining the guard for later coalesced media boundaries.

The same UHF session selected `v4l2slh265dec` for 1280×720 HEVC Main at 25 fps. Decoder input appeared at 10.434 seconds, but no decoder output or video-sink frame was logged before the stop at 12.339 seconds. The receiver then stopped making playback progress, including later YouTube attempts, matching the user's report.

This time the Pi kernel provides direct evidence: receiver thread 9572 is in uninterruptible D state inside `hevc_d_h265_stop`, reached through `hevc_d_stop_streaming`, `vb2_core_streamoff`, and the V4L2 STREAMOFF ioctl. The first blocked-task report at 13:25:26 says the receiver has already been blocked for more than 120 seconds. The service still misleadingly reports active with zero restarts.

A separate synthetic adaptive-media cancellation probe started later, around 13:24:13. Its remaining thread 9652 is blocked in `v4l2_release`; the kernel explicitly reports that its mutex is owned by receiver thread 9572. The receiver hang therefore predates this probe. The probe's userspace deadline and kill did not release its kernel-blocked thread, and the probe was abandoned rather than counted as a passing cancellation test. A debugger attach also could not complete while the target was in that kernel wait; the debugger was terminated and `/proc/9567/status` then confirmed TracerPid 0. No further decoder tests were started against the wedged driver.

The exact installed kernel maps to commit `c8c7494100e99ee05b11aaa4f0588a223a63d1af`. Its HEVC shutdown path waits for outstanding interrupt claims with an uninterruptible, unbounded wait. Killing/restarting UxPlay cannot recover this state; reboot is needed. A similar Pi4 failure is reported for the newer packaged kernel 6.18.39, so an ordinary package upgrade is not a verified fix. Primary references: [installed driver source](https://github.com/raspberrypi/linux/blob/c8c7494100e99ee05b11aaa4f0588a223a63d1af/drivers/media/platform/raspberrypi/hevc_dec/hevc_d_h265.c#L2264), [Pi4 driver report](https://github.com/raspberrypi/linux/issues/7537). A [September driver change](https://github.com/raspberrypi/linux/commit/f2bc178ed43d8f737c10e2ca80598e2a812eab7b) changes slot tracking/release ordering, but its applicability to this exact stream remains unverified.

The next candidate excludes only the `v4l2slh265dec` factory from automatic selection under the explicit `hls-pi4` profile, before any pipelines are created. This affects this receiver process only. Other ranks, including H.264 hardware and the software HEVC decoder, are preserved. Software HEVC rendering speed on the projector remains to validate after reboot; this workaround does not establish 4K compatibility.
