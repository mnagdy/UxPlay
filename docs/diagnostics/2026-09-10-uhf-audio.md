## Interpretation and next correction

The logs do not support fixing this by retaining old audio indefinitely. The real audio transport had already stopped before the video connection appeared. Inspection of surviving RTP object state and stop call sites strongly points to a sender's typed audio TEARDOWN, but that request type was previously logged only at DEBUG. Add explicit bounded lifecycle reasons to distinguish sender teardown, connection destruction and receiver video handover in the next run.

Earlier independent inspection of a failing channel's actual fMP4 bytes found a declared AAC track with no AAC samples, alongside real HEVC video. This run is consistent with the same failure. It does not yet establish why UHF's video export omits sound, or whether the original channel codec affects that export.

A separate concrete protocol inconsistency was found: `/server-info` returned a hardcoded `0x27F` feature mask, while discovery and `/info` returned the configured mask. The [protocol reference](https://github.com/openairplay/airplay-spec/blob/master/index.html#video-httprequests) says these should match. The candidate correction returns the same existing 64-bit mask from `/server-info`, without inventing new capabilities or changing codec settings. It also records when that endpoint is requested. **This is a compatibility correction to test, not a demonstrated audio fix.**

Direct-playback diagnostics are being extended to distinguish first real compressed audio, decoded audio and audio-sink arrival. Codec headers, GAP buffers and empty buffers must not count as audio media. Even a real buffer reaching the sink does not prove physical audibility.

The working receiver remains the rollback boundary. Any next activation must be followed by checks of the actual binary, service recovery, UHF sound and YouTube switching.

## Additional Channel 4 attempts

The user identified the later `sender=other` attempts as the **Channel 4 app**. Sessions 4–6 received master playlists but delivered no media to parsebin. They emitted `gst_buffer_extract: GST_IS_BUFFER` and NULL mini-object unref assertions, followed by `hlsdemux2` stream error code 4 (`TYPE_NOT_FOUND`). This is a different failure stage from UHF's missing audio.

The exact [GStreamer 1.26.2 HLS implementation](https://github.com/GStreamer/gstreamer/blob/1.26.2/subprojects/gst-plugins-good/ext/adaptivedemux2/hls/gsthlsdemux.c#L806) takes a possibly NULL downloaded key buffer, extracts into an allocated zero-filled key, then caches that key without checking the download result or validating a 16-byte key. That path can produce this pair of assertions and misleading subsequent decryption/typefinding failure. It is a source-matched hypothesis for the Channel 4 attempts; the actual selected playlist's encryption method, key format and response status have not been captured. Do not infer FairPlay or a specific DRM requirement from this error alone, and do not claim a generic GStreamer upgrade fixes it.

An isolated synthetic HTTP reproduction on the Pi confirmed the dependency defect: both an AES-128 key endpoint returning HTTP 200 with an empty body and one returning HTTP 404 produced those exact two NULL-buffer assertions followed by `TYPE_NOT_FOUND`, in 104 ms and 103 ms. Both test processes exited with failure and zero decoded audio/video. The fixture used generated/dummy data, software decoders, disabled core dumps and no production changes. Replay script: `/home/mo/uxplay-dev/state/channel4-key-repro-20260910/repro.py`; local copy `/private/tmp/channel4-key-repro.py`. This confirms the library bug but does not identify Channel 4's actual encryption scheme or key response. Its bounded dependency correction is to require a successful download and an exactly 16-byte buffer before caching an AES-128 key; otherwise preserve the existing missing-key error path. No dependency patch is installed.
